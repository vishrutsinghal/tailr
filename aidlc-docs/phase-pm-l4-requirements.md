# PM-L4 — Refresh, Conflict, And Negative Learning Requirements

| ID | Requirement | Acceptance evidence |
| --- | --- | --- |
| PM-L4-001 | Challenge, amend, supersede, revoke, and revalidate are explicit, approval-gated, append-only transitions. | Focused lifecycle tests and digest-chain validation. |
| PM-L4-002 | Policy, graph, symbol, manifest, ownership, source, and validation changes deterministically invalidate captured guidance. | Content/metadata fingerprint fixtures for every invalidator domain. |
| PM-L4-003 | Open challenges and cross-learning conflicts block every affected current record until an evidence-backed resolution. | Navigator negative fixtures show no blocked advice. |
| PM-L4-004 | Conflict resolution is repository-framed; coexistence is allowed only when applicability is demonstrably disjoint. | Overlapping-scope rejection and winner/loser terminal-transition tests. |
| PM-L4-005 | Two independent rejected, stale, possible-harm, or rejected-by-evidence receipts form a negative-learning candidate without copying raw failure material. | Multi-run receipt aggregation and privacy assertions. |
| PM-L4-006 | Negative candidates require explicit promotion or dismissal; promotion creates sanitized avoid-history and revokes contradicted guidance. | Promotion lifecycle test. |
| PM-L4-007 | Corruption, project-frame mismatch, missing evidence, unsafe paths, stale predecessors, and concurrent writes fail closed. | Negative and concurrency assurance tests. |
| PM-L4-008 | CLI, inventory, registry, package, release, docs, review, and refresh surfaces expose one canonical PM-L4 implementation. | Registry, maturity, package, and release checks. |

No dependency is added. Legacy V3 records, refresh actions, governance reports,
candidate stores, and curated projections remain readable for the committed
compatibility window.
