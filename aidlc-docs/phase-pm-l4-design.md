# PM-L4 — Refresh, Conflict, And Negative Learning Design

Learning V3 remains the sole owner of learning content and its append-only
amend, revalidate, supersede, and revoke lifecycle. Learning Refresh remains the
owner of approved operational actions. The new Learning Governance stream owns
only facts that were previously advisory or absent: challenges, pairwise
conflicts, revalidation decisions, and repeated-adverse-evidence candidates.
This keeps the PM-L0 ownership matrix unambiguous.

Each new V3 record captures one closed fingerprint map for source, policy,
graph, symbol, manifest, ownership, and validation domains. Retrieval compares
the current repository snapshot with that saved snapshot and blocks on any
declared change. Pre-PM-L4 records remain valid and use the prior timestamp
compatibility path. Revalidation requires existing project-relative evidence,
appends a V3 record with a fresh snapshot, and does not overwrite history.

The governance ledger is repository-framed, globally sequenced, entity-linked,
digest-chained, sanitized, and protected by the existing cross-platform append
lock. An open challenge blocks one learning. An open conflict blocks both.
Winner resolutions revoke the losing advice; coexistence requires disjoint
task, tag, path, or requirement applicability. Invalid or corrupt governance
evidence blocks all otherwise applicable retrieval.

Negative aggregation reads validated run-local PM-L3 receipts and counts each
receipt once. Two independent adverse receipts after the latest revalidation
form a candidate. Only receipt references, categorical signals, counts, and
learning IDs are retained—never prompts, logs, source snippets, stack traces,
or raw failures. Explicit promotion creates a V3 `avoid-history` record and
revokes the contradicted source record; dismissal retains the audit history but
removes the open-candidate block.
